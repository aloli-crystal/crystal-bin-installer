== v0.1.3 — 2026-04-25

Mode d'installation par lien symbolique. Nouveau drapeau CLI
`-l` / `--link` (et clé de configuration équivalente `link: true`)
qui installe chaque binaire comme un lien symbolique vers
`bin/<cible>` dans le projet source, au lieu d'en copier le
fichier. Tout `shards build` ultérieur dans un projet est alors
immédiatement reflété dans `~/bin` sans avoir à relancer
l'installeur — très pratique en itération sur un outil que vous
utilisez aussi quotidiennement.

* La cible du lien est toujours un chemin absolu, pour que le lien
  survive à un `--dest` relatif ou à un futur déplacement de `~/bin`.
* La destination est nettoyée et recréée à chaque exécution, pour
  qu'un basculement entre `--link` et le mode copie par défaut soit
  idempotent (pas de liens cassés laissés derrière, pas de copies
  périmées).
* `--no-link` est fourni comme contrepartie pour forcer le mode
  copie depuis la ligne de commande même si `link: true` figure
  dans le fichier de configuration.
* La ligne de succès de chaque installation affiche `lié : <chemin>`
  au lieu de `installé : <chemin>` lorsque le mode lien est actif,
  pour rendre le choix explicite dans le journal d'exécution.
* 4 nouveaux tests unitaires couvrant : le parsing de la clé de
  configuration (`link: true`), la création du lien pointant sur
  la source, le mode copie préservé quand `link: false`, et le
  remplacement idempotent d'une destination existante. **11 tests
  unitaires, tous verts.**

== v0.1.2 — 2026-04-22

* Ajout d'un fichier de configuration persistant au niveau utilisateur,
  chargé par défaut depuis `~/.bin-installer.yml`. Clés
  supportées : `dir`, `dest`, `release`, `fetch`, `force`, `skip`
  (liste). Le chemin peut être surchargé avec `--config CHEMIN`.
* Ordre de précédence désormais : valeurs par défaut < fichier de
  configuration < options en ligne de commande. `--skip` est additif
  avec le fichier de configuration (union des deux listes) ; toutes
  les autres options surchargent.
* La bannière d'aide du CLI documente l'emplacement du fichier de
  configuration et la liste des clés supportées.

== v0.1.1 — 2026-04-22

* Quand un projet déclare une seule cible, le binaire installé prend
  désormais le nom du projet (répertoire) plutôt que celui de la cible.
  Cela évite que des noms de cibles génériques polluent `~/bin` et
  masquent d'autres outils sur le `$PATH` (par exemple `deploy`
  s'installait auparavant sous le nom `deploy`).
* Les projets avec plusieurs cibles conservent le comportement
  précédent : chaque binaire est installé sous son propre nom de cible.

== v0.1.0 — 2026-04-22

Première version publique.

* Parcourt un répertoire source (par défaut `~/prod-crystal`) et détecte
  chaque projet Crystal déclarant une section `targets:` dans son
  `shard.yml`.
* Vérifie la synchronisation git face à `origin/production` : branche
  courante, arbre de travail propre, distant à jour.
* Lance `shards install --production` puis `shards build` (avec
  `--release` sauf si `--dev` est passé).
* Copie le binaire produit dans le répertoire de destination (par défaut
  `~/bin`).
* Options CLI : `--dir`, `--dest`, `--dev`, `--skip`, `--dry-run`,
  `--no-fetch`, `--force`, `-v`, `-h`.
* Affiche un récapitulatif coloré en fin d'exécution (installés / échecs
  / exclus).
